# tabloda.uz — табло ближайших поездов, электричек и самолётов Узбекистана

Статический сайт: данные лежат в JSON, страница их читает. Бэкенда нет,
хостинг — GitHub Pages, домен tabloda.uz.

Три раздела. **Поезда** (`index.html`): 14 городов, оба направления,
раскрытие маршрута по клику, номера платформ. **Самолёты**
(`flights.html`): 14 аэропортов, вылет и прилёт, фактическое время,
терминалы, стойки регистрации и багажные ленты. **Электрички**
(`suburban.html`): 22 пригородных маршрута по 11 регионам, табло станции
как у поездов (отправление и прибытие), отмены на сегодня и завтра,
строка раскрывается в список остановок рейса.

Отдельная страница — **карта поезда** (`train-map.html`): примерное
положение поезда между станциями сейчас. Позиция считается из расписания,
живых координат нет: по времени остановок и полю `offset` в
`routes.json` (номер суток от начала рейса, так учтён переход через
полночь) поезд ставится на отрезок между двумя станциями. Карта — Leaflet 1.9.4 и
плитки OpenStreetMap, тёмная тема (инверсия плиток), три языка,
подписи станций всегда видны. Открывается ссылкой «Показать на карте» из
строки поезда в `index.html`, параметры в адресе: `number`, `here`, `dir`,
`time`, `tomorrow`. Координаты станций — `data/station_coords.json`.

Общее для всех разделов: три языка (узбекский по умолчанию), светлая и тёмная
темы. Выбор языка, темы, города и аэропорта хранится под ключами
`board-lang`, `board-theme`, `board-city`, `board-airport` — общими,
чтобы переход между разделами ничего не сбрасывал. Электрички помнят
ещё станцию и регион (`board-station`, `board-region`).

Палитра, шапка, часы, языки, вкладки, кнопки выбора и строки табло
вынесены в `assets/common.css` и правятся только там. В самих HTML осталось
специфичное: маршрут со стопами у поездов, статусы и терминалы у
самолётов. До 29 августа 2026 стили дублировались в двух файлах, и
выравнивание кеглей пришлось делать скриптом сравнения.

С `viasales.uz` работает переадресация на tabloda.uz.

## Устройство

```
Яндекс.Расписания ──► build_yandex.py ──► seed.json ──► i18n.py ──► sync.py
                            │                              ▲            │
                            ▼                              │            ▼
                      .cache/threads ──► routes.py     extra.json   schedule.json
                                              │        brands.json       │
                                              ▼                          ▼
                                        routes.json ────────────► index.html
tm.md.uz ──────────► live.py ─────────► live.json ──────────────────────┘

uzairports.com ────► live_flights.py ──► flights_live.json ──► flights.html
                                                    ▲
                                       cities.json, statuses.json

ticket.elektropoyezd.uz ─► elektropoyezd.py ─► suburban.json ─► suburban.html
                                   ▲
                          station_names.json

routes.json ─► station_coords.py ─► station_coords.json ─► train-map.html
suburban.json ─► suburban_coords.py ─► suburban_coords.json  (пока не читается)

avtoticket.uz ─► buses_watch.py ─► buses_state.json, buses_log.jsonl
                                   (замер, на сайт не выводится)
```

Расписание поездов пересобирается раз в неделю, живое табло станций —
раз в час (7-я минута), табло аэропортов — трижды в час (12, 32, 52-я
минуты), электрички — раз в час (47-я минута). Минуты разнесены, чтобы
шаги не толкались за одну группу `data-write`. Трижды в час у аэропортов
не от жадности: GitHub выполняет расписание через раз, и при одной
попытке выходило шесть прогонов в сутки вместо двадцати четырёх. Посетитель
скачивает готовые JSON, к сторонним API со страницы не уходит ни одного
запроса.

Workflow лежат в `.github/workflows/`: `schedule-sync.yml` (понедельник,
04:00 UTC), `live-sync.yml`, `flights-sync.yml`, `suburban-sync.yml` и
`buses-watch.yml` (каждые три часа, 17-я минута). Все пять пишут в
репозиторий через одну группу `data-write`.

## Источники и как их искали

### Поезда

**Яндекс.Расписания** — основной. Ключ бесплатный, по заявке. Станции
задаются кодами системы express (те же, что у УТЙ: Ташкент-Центральный
2900001, Южный 2900002, Самарканд 2900700). Эндпоинт `/thread/` отдаёт
маршрут целиком со всеми остановками — благодаря ему страна собирается
из двух станций-якорей.

**tm.md.uz** — живые табло станций, открытый доступ без авторизации.
Даёт платформы, конкретные даты, наличие мест. Семь известных адресов:

    tashkent-central  proxyS.php        urgench   proxyU.php
    tashkent-south    proxyYu.php       bukhara   proxyB.php
    samarkand         proxy.php         qarshi    proxyKarshi.php
                                        andijan   proxyAndijon.php

Имена непоследовательные (ранние — короткие коды, поздние — полные
названия), вычислить нельзя, только подсмотреть в DevTools.

**eticket.railway.uz** — Angular, данных в HTML нет, запросов к своему
API при загрузке не видно, «Скачать расписание» за авторизацией. Отсюда
брали бренды поездов вручную.

**uzrailpass.uz/ru/pages/poezd-jadvali** — единственная страница с
расписанием в обычном HTML. Но данные устарели: 710Ф там 8:40, а по
трём другим источникам 8:37. Не используем.

### Самолёты

**uzairports.com** — единственный источник, авторизации нет. Один
маршрут на все аэропорты и оба направления:

    /flights/{event}?status={event}&airport={IATA}

JSON-эндпоинта нет, страница рендерится Laravel'ом на сервере, но
разметка семантическая (`flight-result__content`, `flight-code`,
`terminal`), парсится устойчиво. Заголовок `Accept: application/json`
и префиксы `/ru/`, `?lang=ru` игнорируются — отдаётся всегда узбекский.

Четырнадцать аэропортов: TAS, SKD, BHK, UGC, NMA, AZN, FEG, KSQ, NCU,
TMJ, NVI плюс вертолётные площадки Silk Avia RBZ (Шахрисабз), OMN
(Зомин), IYO (Сариасия). Код AFS (Зарафшан) отвечает пустой страницей.

**Яндекс.Расписания для самолётов** — проверен и отвергнут. Отдаёт
плановую сетку и тип борта, которых нет на табло, но не знает части
внутренних рейсов Silk Avia (UH704, UH722, UH756, UH758, UH762) и
аэропорта Сариасия, а дни курсирования отдаёт текстом с сезонной
границей («вс по 18.10»). Разведочный скрипт `flights_probe.py`
оставлен на случай, если табло изменит разметку.

### Электрички

**ticket.elektropoyezd.uz** — сайт продажи билетов «Shahar atrofida
yo'lovchi tashish» (пригородная дочка УТЙ). Фронтенд на Vite ходит в
открытый JSON-API, ключ не нужен:

    GET /api/routes                   22 маршрута, сгруппированы по регионам
    GET /api/routes/{id}?date=Y-M-D   маршрут, рейсы, отмены и опоздания на дату
    GET /api/trains/{id}              остановки рейса, без даты

Язык — заголовком `Accept-Language: ru|uz|en`. Названия переведены,
причины отмен — нет (приходят на узбекском). Дни курсирования —
`operating_day_numbers`, 1…7, нумерация ISO (1 — понедельник). Источник
этого не пишет: сначала выведено по нитке Нукус–Ургенч с особым
расписанием по «4», 29.09.2026 сверено с календарём на сайте продажи
билетов. Параметр `date` на состав рейсов не влияет, только на статус.
Остановки рейса — отдельный запрос `/api/trains/{id}` на каждый рейс,
по нему страница раскрывает строку.
Основной сайт elektropoyezd.uz расписания не содержит. Система билетов
висит с баннером «работает в тестовом режиме».

## Подводные камни (все проверены на данных)

### Поезда

**Цифры номера не идентифицируют рейс.** Это главная ловушка проекта,
подводила трижды: при сравнении с Яндексом, при расчёте отклонений и при
подстановке маршрутов. 054Ф идёт Ташкент → Кунград, 054Щ обратно; 056Ч и
056Ж — встречные. Суффиксы плавают между источниками (латиница у Яндекса,
кириллица на табло), однозначного соответствия нет. Сшивать можно только
по цифрам **вместе с направлением или временем**.

**Дни курсирования выводятся эмпирически.** Яндекс отдаёт их текстом
(«ежедневно», «кроме 3 сентября»), разбирать ненадёжно. Опрашиваем
расписание на 14 дней: каждый день недели попадает дважды, разовые
пропуски видно. При семи днях любая дырка давала неверный шаблон.

**Чётные и нечётные числа шаблоном не описываются.** 071Ф и 072Ф на Алат
ходят по числам месяца, а не по дням недели, и всегда светятся в списке
«дни под вопросом». Чинится только хранением конкретных дат.

**Сдвиг суток берётся из дат ответа**, а не выводится из порядка времён.
Так корректно считаются и переход через полночь, и рейсы длиннее суток.

**Бренд по номеру не угадывается.** Первая версия считала все 7xxF за
Афросиёб — неверно: 710Ф это Sharq, 716Ф Nasaf, 730Ф O'zbekiston.
Хранится в `brands.json`, перепроверено по разделу «АФРОСИЁБ» на
uzrailpass.

**Порядок команд важен.** `i18n.py` и `sync.py` работают с тем, что лежит
в `seed.json` на момент запуска. Прогон до сборки пересоберёт старый
набор, и будет казаться, что сборка не сработала.

**`rm schedule.db` перед `sync.py --seed`** обязателен, иначе новые поля
в базу не попадут: скрипт увидит те же записи и напишет «0 добавлено».

### Самолёты

**Сотня — это лимит, а не количество.** У Яндекса `limit=100` по
умолчанию; при 110 рейсах десять невидимы. Та же ошибка, что с 485
записями поверх 574. `fetch_schedule` ходит постранично и при неполной
выдаче отказывается писать.

**Имя перевозчика в источнике бывает неверным.** Яндекс резолвит код UH
в «Uzbekistan Helicopters», хотя это Silk Avia — внутренние рейсы на
Бухару, Термез, Карши, Самарканд, Андижан, Фергану. Едва не отфильтровали
как вертолётные. Тот же класс ошибки, что с брендами 7xxF.

**Табло отдаёт трое суток сразу**, причём дальние дни неполны
(29.08 — 81 запись, 30.08 — 112, 31.08 — 45). Дублей нет, фильтровать
надо по `date`.

**Поле `check-in` значит разное по направлениям**: у прилёта это
багажная лента, у вылета — стойки регистрации. Подпись встроена в
значение (`Yuk Karusel 02`), поэтому берём только вложенный `<span>`,
а подпись подставляем свою.

**Статусы приходят строкой на узбекском**, но их конечное число: пять
фиксированных и два шаблона с подстановкой времени. Приводятся к коду в
`normalize_status`, переводятся через `statuses.json`. Отдельно
обрабатывается `xx:xx gacha kechiktirildi` — задержка без известного
времени.

**HTML-сущности надо декодировать.** `Farg&#039;ona` в разметке —
норма, `clean()` прогоняет через `html.unescape`.

**Источник переделывает разметку молча.** 30 сентября 2026 номер рейса
переехал из `<span class="highlight">` в ссылку на карточку рейса
(`<a href=".../flight/328351" class="highlight">`), и выражение перестало
совпадать — номер пропал у всех 718 записей разом, остальные поля
остались целы. Заметили случайно. Теперь выражение цепляется за
`class="highlight"` без привязки к тегу, а из ссылки забирается
`flight_id` — он устойчивее номера. Проверять стоит не только то, что
записи собрались, но и что ключевые поля непустые.

**Имена перевозчиков в источнике непостоянны.** Тогда же Silk Avia стала
приходить как «UH», Turkish как «Turk Hava Yollari», Centrum Air через
дефис, часть названий капсом и с юрформой («Air company Somon Air LLC»).
Код IATA при этом стабилен, поэтому имена берутся из `airlines.json` по
коду, а пришедшее из источника остаётся запасным вариантом.

**Сеть маршрутов растёт быстрее, чем кажется.** За полторы недели
добавилось семнадцать направлений — Токио, Бангкок, Мумбаи, Прага,
Чэнду. Незнакомый код показывается на сайте как есть (`NRT` вместо
Токио), поэтому `live_flights.py` в конце прогона печатает коды,
которых нет в `cities.json`. Строка видна в отчёте Actions. Часть
названий источник не переводит вовсе (`airport.HYD`), их приходится
определять по IATA.

**Горизонт разный по направлениям.** На вылет приезжают заранее, поэтому
5 часов; встречающему хватает 3. Улетевший рейс убирается сразу,
прилетевший висит ещё полчаса — полезно видеть, что борт сел.

**У мелких аэропортов в горизонт часто не попадает ничего.** У Навои
три рейса за трое суток, у вертолётных площадок один-два. Пустой список
выглядел поломкой, поэтому показывается ближайший рейс за окном с
пояснением и датой. Обратный отсчёт при этом обрывается на 12 часах:
«через 43 ч 31 мин» ничего не говорит, вместо него «завтра» или
«послезавтра», а дальше — только дата.

### Электрички

**Список — не весь источник.** Маршрут 29 (Коканд — Наманган — Андижан)
из `/api/routes` убран, но по id отвечает, рейсов в нём ноль. Скрипт
перебирает id до максимума из списка плюс шесть и выносит такие в
проблемы. Проверка на усыхание считает только маршруты из списка,
иначе перебор замаскировал бы сбой.

**Станции у обратных рейсов перепутаны.** У 7092, 7207, 7055, 6461,
6413, 6352 `origin_station`/`destination_station` совпадают с прямым
рейсом. Верить надо `direction`; страница так и делает, скрипт
отмечает это как info.

**Рейс не между концами маршрута — это не ошибка вёрстки.** 7049 идёт
Бекабад → Ташкент Южный, хотя маршрут от Ташкент-Центрального. В
«Кунград — Мискин» оба рейса на деле Нукус ↔ Мискин.

**Один номер — две нитки.** 6351/6352 стоят и в «Кунград — Мискин»,
и в «Нукус — Мискин» с разным временем прибытия. 6354 Нукус–Ургенч —
два поезда с одним номером: по четвергам в 10:00, в остальные дни в
05:50. Ключ поезда — `id` из API, не номер.

**Названия станций у источника и у Яндекса расходятся.** «Ташкент Южный» и
«Ташкент-Южный», «Сариасия» и «Сарыасия», «Коканд (вокзал)» и «Коканд 1».
`suburban_coords.py` сравнивает нормализованные названия и при нуле или
нескольких кандидатах не угадывает, а отказывается писать; вручную —
таблицы `YANDEX_CODE` и `MANUAL` в самом скрипте. Координаты нужны у
каждой остановки действующих рейсов, а не только у концов маршрута (около
140 станций), поэтому часть станций сопоставляется постепенно. Станция 125
(Kokand Ring) пока без координат, действующих рейсов через неё нет.
Результат — `data/suburban_coords.json`, но карта его пока не читает.

## Карта поезда

`train-map.html`, устройство описано выше. Что важно помнить:

- Позиция **приблизительная**: это интерполяция по расписанию, а не GPS.
  Опоздание поезда карта не видит.
- Координаты станций берутся из Яндекс.Расписаний (`stations_list`) по
  названию: 06.09.2026 совпало 59 из 59, дублей координат не было.
  `station_coords.py` — разовый инструмент, запускать вручную, когда в
  `routes.json` появились новые станции; нового в автосборку не встроено.
- Плитки — OpenStreetMap, подпись на карте `© OpenStreetMap`. Данные
  поездов — Яндекса, поэтому на карте стоит и его атрибуция (см.
  «Обязательства»).
- `build_uz_outline.py` разово собирает контур страны в
  `assets/uz-outline.json` (Natural Earth, CC0). В `train-map.html` файл
  пока не подключён.

## Автобусы (замер, не раздел сайта)

Междугородние автобусы пока **не выведены на сайт**. Источник —
`wapi.avtoticket.uz`, агрегатор восьми систем продаж, без авторизации:
`GET /api/api-locations` (справочник регионов и станций) и
`POST /api/api-trips` по парам регионов (СОАТО). Из облачной среды Claude
сайт закрыт прокси, с Mac и из GitHub Actions отвечает.

`buses_watch.py` — не сборщик, а измерительный прибор на неделю-две: раз в
три часа (`buses-watch.yml`) опрашивает рейсы из Ташкента (регион 1726)
на три дня вперёд, склеивает по `(api_id, id)` и сравнивает с прошлым
прогоном. Пишет `data/buses_state.json` и `data/buses_log.jsonl`
(события `add`, `gone`, `chg`, `lead`). Сводка — `buses_stats.py`. Ответ
нужен на вопрос «как часто и за сколько часов до отправления рейс
меняется»: от него зависит частота настоящего сборщика. Первый базовый
снимок 30.09.2026, итоговый разбор около 07.10.

Главные ловушки (все проверены на данных, подробности и цифры — в
`claude/buses-findings.md` в знаниях проекта): запрос по региону отдаёт
транзит, и почти всё дубли, поэтому 56 уникальных рейсов в сутки при
десятках записей; ключ рейса не должен включать `redirect_url` (он зависит
от пары регионов); `arrive_at` ненадёжно и показывать его нельзя;
`to_name_*` — запрошенная пара, а не конечная остановка; у станций нет
координат (0 из 103), а для карты они нужны.

## Чего нет

**Фактических задержек у поездов — и, похоже, не будет.** Все четыре
железнодорожных источника отдают плановое время. `live.py` копил
историю отклонений несколько дней; на 122 наблюдениях отклонения нашлись
у четырёх рейсов, и все они постоянные:

    urgench  752Ж  40 раз  +6 всегда
    urgench  751М  39 раз  -5 всегда
    urgench  126Ф  34 раза +8 всегда
    bukhara  056Ч   9 раз  +10 всегда

Постоянная величина означает расхождение между табло и расписанием, а не
опоздание. Настоящих задержек за всё время наблюдений не было ни одной,
так что показывать на сайте нечего. Четыре рейса при желании можно
поправить файлом переопределений по образцу `extra.json` — вероятнее,
что права станция, а не сборка. У самолётов фактическое время есть
прямо в источнике.

**733Ф и 734Ф у Яндекса отсутствуют**, хотя на сайте УТЙ есть и билеты
продаются. Добавлены вручную через `extra.json`, который подмешивается
после каждой сборки.

**Типа борта у самолётов.** Есть только у Яндекса (в 83% случаев), на
табло нет. Единственная причина, по которой к нему стоило бы вернуться.

**Дней курсирования у самолётов.** Табло знает трое суток вперёд, и
этого достаточно при суточном горизонте планирования.

**Мест и цен** — есть в источниках, устаревают за минуты.

## Команды

Расписание поездов, при смене графика (дважды в год):

```bash
export YANDEX_RASP_KEY=...
python3 build_yandex.py --apply     # ~5 минут, 69 маршрутов
python3 i18n.py                     # города, переводы, бренды, extra.json
rm schedule.db
python3 sync.py --seed
python3 routes.py                   # маршруты из .cache/threads
```

Живые табло, часто (обычно через Actions, вручную — для проверки):

```bash
python3 live.py                     # станции: платформы, отклонения
python3 live.py --history           # разброс отклонений за всё время
python3 live_flights.py             # аэропорты, ~700 записей за трое суток
python3 live_flights.py --airport TAS --event departure
python3 live_flights.py --file /tmp/tas.html --airport TAS  # разбор без сети
python3 elektropoyezd.py            # электрички, ~90 запросов, полминуты
python3 elektropoyezd.py --dry-run  # снять и показать проблемы, не записывая
```

Электрички без сети, на снимке API от 28.09.2026:

```bash
python3 tests/make_fixture.py tests/snapshot_2026-09-28.txt /tmp/fx.json.gz
python3 elektropoyezd.py --fixtures /tmp/fx.json.gz --date 2026-09-28 --dry-run
```

Координаты и замер автобусов (разовые, вручную; координатам нужен ключ):

```bash
python3 station_coords.py           # координаты станций поездов
python3 suburban_coords.py          # разведка, ничего не пишет
python3 suburban_coords.py --apply  # записать, если нашлось всё
python3 buses_watch.py --dry-run    # прогон замера без записи состояния
python3 buses_stats.py              # сводка по журналу замера
```

Разведка:

```bash
python3 yandex.py --probe                 # проверить ключ и коды станций
python3 yandex.py --route samarkand       # маршрут рейса с кодами остановок
python3 build_yandex.py --inventory       # все станции, что встретились
python3 compare.py                        # сравнить два набора данных
python3 flights_probe.py --airports       # коды аэропортов у Яндекса
python3 flights_probe.py --fields s9600397 --date 2026-08-30
```

| `statuses.json` | статусы рейсов по коду, три языка |

## Обязательства

По условиям API Яндекс.Расписаний на сайте должно стоять указание
источника: «Данные предоставлены сервисом Яндекс Расписания» со ссылкой
на rasp.yandex.ru, шрифтом не меньше основного и тем же цветом. Стоит в
`index.html` над подвалом отдельным блоком — убирать нельзя. На
`train-map.html` карта построена на тех же данных, там тоже стоит ссылка
на «Яндекс Расписания». Требование
распространяется на все места, где показываются данные Яндекса, включая
будущего телеграм-бота.

**На `flights.html` этой атрибуции нет и быть не должно** — данные
Яндекса там не используются. Вместо неё указан uzairports.com.
