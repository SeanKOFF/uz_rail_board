# Табло ближайших поездов — Узбекистан

Статический сайт: расписание лежит в `data/schedule.json`, страница его
читает. Бэкенда нет. Работает на GitHub Pages.

14 городов, оба направления, три языка (узбекский по умолчанию).

## Откуда данные

**Расписание — API Яндекс.Расписаний.** Ключ бесплатный, по заявке.
Условие использования — указание источника: текст «Данные предоставлены
сервисом Яндекс Расписания» со ссылкой на rasp.yandex.ru, шрифтом не
меньше основного и тем же цветом. Стоит в `index.html` над подвалом,
отдельно от приглушённого текста — убирать нельзя.
Станции задаются кодами системы express — теми же, что использует УТЙ.
Маршрут каждого рейса запрашивается целиком, поэтому промежуточные
станции получаются автоматически: одна станция-якорь раскрывает страну.

**Платформы — табло станций на `tm.md.uz`.** Открытый эндпоинт, без
авторизации. Даёт номер пути, конкретные даты и наличие мест.

**Бренды — `brands.json`, собран вручную.** Яндекс их не отдаёт: в
`transport_subtype` у него общие категории. Взято с eticket.railway.uz,
перепроверено по разделу «АФРОСИЁБ» на uzrailpass.uz.

Сверка четырёх источников (Яндекс, eticket, uzrailpass, tm.md.uz)
показала: страница расписания на uzrailpass устарела — там 710Ф в 8:40,
у остальных трёх 8:37. Времена берём у Яндекса.

## Сборка

Расписание — редко, при смене графика (дважды в год):

```bash
export YANDEX_RASP_KEY=...
python3 build_yandex.py --apply      # ~5 минут, 69 маршрутов
python3 i18n.py                      # города, переводы, бренды
rm schedule.db
python3 sync.py --seed
```

Живое табло — часто, если нужны актуальные платформы:

```bash
python3 live.py
```

**Порядок имеет значение.** `i18n.py` и `sync.py` обрабатывают то, что
лежит в `seed.json` на момент запуска. Если прогнать их до сборки,
пересоберётся старый набор, а новый останется за бортом — и это будет
выглядеть так, будто сборка не сработала.

**Маршруты кэшируются** в `.cache/`. Они меняются только вместе с
графиком, поэтому повторный прогон почти не расходует лимит ключа.
Чтобы заставить перечитать — удалить папку.

**Неполная выдача не применяется.** Если хоть один маршрут не получен
(обычно из-за лимита), `--apply` откажется писать и выйдет с ошибкой.
Лимит суточный: повторить через несколько часов, второй прогон пойдёт
из кэша. Без этой защиты неполный набор тихо затирает полный — так
485 записей однажды легли поверх 574.

На сайт заливаются `index.html`, `data/schedule.json`, `data/names.json`,
`data/live.json`.

## Что учтено (всё проверено на данных)

**Сдвиг суток берётся из дат.** Ответ Яндекса содержит полные даты, а не
только время, поэтому переход через полночь и многосуточные рейсы
(Москва — двое с лишним суток) считаются точно, а не выводятся из
порядка времён.

**Стоянки настоящие.** У транзитного поезда на промежуточной станции два
времени: 712Ф в Самарканде прибывает 23:41, уходит 00:02. Ручная сборка
давала одну метку — это было приближение.

**Суффиксы номеров плавают.** 054Ф, 054Щ и 054 — один поезд. Сшивка
везде идёт по цифрам.

**Бренд по номеру не угадывается.** Первая версия считала все 7xxF за
Афросиёб — неверно: 710Ф это Sharq, 716Ф Nasaf, 730Ф O'zbekiston.

**Названия приходят на трёх языках** и с уточнениями вокзалов. Город и
уточнение хранятся раздельно, чтобы «Ташкент-Южный» переводился целиком,
а не наполовину.

**Список городов явный, а не по трафику.** Отбор по числу рейсов вымывал
Нукус и Хиву и притаскивал придорожные станции. Список — `SHOW` в
`build_yandex.py`.

## Чего нет

**Фактических задержек.** Все четыре источника отдают плановое время.
`live.py` умеет сравнивать табло с расписанием и показывать отклонение,
но постоянное расхождение означает разные редакции расписания, а не
опоздание. Настоящая задержка плавает — различить можно только
наблюдением за несколько дней.

**Пригородных электричек.** Их больше и график меняется чаще.

**Мест и цен.** Есть в источниках, устаревают за минуты.

**Двух рейсов, которые есть у УТЙ.** 733 и 734 (Ташкент — Наманган —
Андижан) Яндекс не отдаёт. Напоминание, что он посредник, а не
первоисточник.

## Файлы

| Файл | Назначение |
| --- | --- |
| `index.html` | сайт: города, направление, отсчёт, три языка |
| `build_yandex.py` | сборка расписания через маршруты рейсов |
| `yandex.py` | клиент API: `--probe`, `--route`, `--inventory` |
| `live.py` | табло станций: платформы, даты, отклонения |
| `i18n.py` | города, переводы, бренды |
| `sync.py` | база, сверка, экспорт JSON |
| `compare.py` | сравнение двух наборов данных |
| `brands.json` | бренды по номерам |
| `stations.json` | коды станций из бандла сайта УТЙ |

Скрипты ручной сборки — `from_table.py`, `build_station.py`,
`parse_direction.py` — оставлены как запасной путь на случай, если ключ
Яндекса отзовут. Они собирают данные из текста, скопированного со
страниц eticket.railway.uz.

## Полезные команды

```bash
python3 yandex.py --probe                    # проверить ключ и коды
python3 yandex.py --route samarkand          # маршрут рейса с кодами станций
python3 build_yandex.py --inventory          # все станции, что встретились
python3 build_yandex.py                      # собрать, не трогая seed.json
python3 compare.py                           # сравнить с текущими данными
python3 live.py --show                       # табло станций
```

## Автообновление

Две задачи в `.github/workflows`, обе с кнопкой ручного запуска:

| Задача | Когда | Что делает | Нужен ключ |
| --- | --- | --- | --- |
| `schedule-sync.yml` | понедельник, 09:00 | пересобирает расписание из Яндекса | да |
| `live-sync.yml` | каждый час | снимает табло станций, копит историю | нет |

Ключ кладётся в Settings → Secrets and variables → Actions → New
repository secret, имя `YANDEX_RASP_KEY`. В коде его нет и быть не должно.

Ещё нужно разрешить задачам писать в репозиторий: Settings → Actions →
General → Workflow permissions → Read and write.

**Задачи запускают скрипты из репозитория, а не с твоего компьютера.**
Значит, после правки любого скрипта его надо залить, иначе в понедельник
соберётся старой версией и закоммитит результат поверх хорошего. Если
локально что-то поменял и залить не успел — выключи задачу: Actions →
нужная задача → три точки → Disable workflow.

**Защита от порчи данных.** Если Яндекс вернёт меньше 80% прежнего числа
записей, недельная задача прерывается и ничего не применяет: скорее это
сбой источника, чем массовая отмена рейсов. Сайт продолжает работать на
прошлых данных.

Обе задачи пишут в одни и те же файлы, поэтому объединены в общую группу
`concurrency` — одновременно не запустятся.
